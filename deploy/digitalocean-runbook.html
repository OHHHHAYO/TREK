00

What you are actually deploying

TREK is one stateful container. The NestJS API, the compiled React app, and the real-time WebSocket layer all listen on a single port (3000). Its database is SQLite at /app/data/travel.db, and uploaded photos, documents and trip files land on the local filesystem at /app/uploads. There is no Postgres driver and no S3 client anywhere in the server code — I checked.

Two consequences drive every decision below:

  • It needs a real disk that survives restarts. That rules out DigitalOcean App Platform, whose filesystem is ephemeral — your trips and uploads would vanish on every redeploy.
  • It cannot be horizontally scaled. Two containers writing one SQLite file corrupts it. One droplet, one container, vertical scaling only.

So: a single Droplet running Docker, with Caddy in front terminating TLS and proxying to TREK over a private container network. TREK itself publishes no host port at all.

Why 2 GB is enough

Building the image is the only memory-hungry thing this server ever does, so the tier is chosen by measuring that, not by guessing. Both build stages were profiled on this codebase:

Build stageToolPeak memory
Client bundleVite / Rollup — sourcemaps off1.11 GB
Server compiletsc0.56 GB
Native better-sqlite3node-gyp / C++~0.4 GB
Peak — the stages run sequentially, so these do not add up≈ 1.1 GB

Against 2 GB, with Ubuntu and the Docker daemon taking roughly 400 MB between them, that leaves around 500 MB of headroom at the worst moment — plus the 4 GB swap file from stage 07 as a backstop. TREK at rest idles well under 1 GB, so running it was never the constraint.

If you want to go cheaper still

The 2 GB / 1 vCPU tier (≈ $12/mo) also fits in memory. You give up the second core, which mostly costs you time during npm ci and the C++ compile — figure on a first build closer to 30 minutes than 15. Everything afterwards is identical.

Resizing later is easy in one direction: Resize → CPU and RAM only is reversible. The disk-inclusive resize is not — growing the disk is a one-way door.

Prices move; confirm the real figure on the droplet creation screen before you click Create.

01

Make an SSH key

Do this first — DigitalOcean asks for the public half while creating the droplet, and a droplet created without one emails you a root password instead, which is worse in every way. Use a dedicated key rather than your existing ~/.ssh/identity, so revoking access to this server never touches anything else.

Your Mac · Terminal
ssh-keygen -t ed25519 -C "trek-droplet" -f ~/.ssh/trek_do

# Copy the PUBLIC half to your clipboard (note the .pub)
pbcopy < ~/.ssh/trek_do.pub

Give it a passphrase when prompted, then add it to your keychain so you are not retyping it:

Your Mac · Terminal
ssh-add --apple-use-keychain ~/.ssh/trek_do
Never share this

Send only trek_do.pub anywhere. The file without .pub is your private key — it never leaves this machine, never gets pasted into a web form, never goes in the repo.

Give the droplet a short name

Every later stage would otherwise start with ssh -i ~/.ssh/trek_do trek@YOUR_DROPLET_IP. An SSH config entry turns all of that into ssh trek — and scp, rsync and git pick it up for free.

Your Mac · Terminal~/.ssh/config
Host trek
    User trek

Host trek-root
    User root

# Shared by both. SSH takes the first value it finds for each keyword,
# so the User lines above win and these fill in the rest.
Host trek trek-root
    HostName DROPLET_IP
    IdentityFile ~/.ssh/trek_do
    IdentitiesOnly yes
    AddKeysToAgent yes
    UseKeychain yes
    ServerAliveInterval 60
    ServerAliveCountMax 3
Your Mac · Terminal
chmod 600 ~/.ssh/config

IdentitiesOnly yes stops SSH offering every key you own, which is what causes too many authentication failures. ServerAliveInterval keeps a session alive through the long image build in stage 09. Two hosts, because stages 07 and 08 run as root, before the trek user exists.

Fill in the IP at stage 04

DROPLET_IP is a placeholder — the droplet does not exist yet. Until you replace it, connections fail with Could not resolve hostname DROPLET_IP, which is the reminder.

03

Register a domain and hand DNS to DigitalOcean

DigitalOcean does not sell domains. It hosts DNS for free, but the registration itself happens at a registrar. The one requirement this deployment imposes is that your registrar must let you point the domain at third-party nameservers — DigitalOcean's. Most do. One notable one does not.

Registrar.com / yrCustom nameserversVerdict
Porkbun ≈ $10–11 Yes Recommended. Registration and renewal cost the same — no promo trap. WHOIS privacy, DNSSEC and email forwarding included free.
Namecheap ≈ $11 yr 1, ≈ $16 after Yes Fine. Bigger, longer-established, free WHOIS privacy. You pay for that in the renewal step-up.
Cloudflare Registrar ≈ $10 at cost No Cheapest, but incompatible with stage 03 as written — see below.
GoDaddy cheap yr 1, steep after Yes Avoid. Aggressive upsells and renewal pricing well above the others.
Why Cloudflare Registrar is excluded

Cloudflare sells domains at wholesale cost as a benefit of using Cloudflare's own DNS, and its registration agreement does not permit changing the nameservers — to move them you have to transfer the domain to another registrar. So you cannot delegate to DigitalOcean, and this stage breaks.

That is a constraint, not a defect. If you would rather use Cloudflare, it is a perfectly good alternative: register there, skip DigitalOcean DNS entirely, and create the A record in Cloudflare's own dashboard instead. Leave it DNS only (grey cloud, not orange) — proxying puts Cloudflare's TLS in front of Caddy's, which complicates certificate issuance for no benefit here.

Whichever you pick, expect $10–15/year for a .com. Prices quoted here are approximate — confirm at checkout.

Buying it at Porkbun

Roughly ten minutes, most of it deciding on a name.

  1. Search the name. Go to porkbun.com and type your idea into the search box. Available names appear with a price; taken ones are struck through.
  2. Read the price row, not the headline. Porkbun shows registration and renewal side by side. On a .com they should match at roughly $10–11. If a TLD catches your eye with a $1 first year, look at the renewal column before you fall in love — that is where the money is.
  3. Add to cart, then decline every add-on. You will be offered web hosting, email hosting, and an SSL certificate. You need none of them: TREK is your hosting, and Caddy issues your certificate free in stage 09.
  4. Create the account. Email and password. Use a password your manager generated, and turn on two-factor auth under account settings once you are in — whoever controls this domain controls where your app's traffic goes.
  5. Enter real contact details. ICANN requires them to be accurate, and a domain registered with fake details can be suspended. They will not be public — WHOIS privacy is on by default and free, so queries return Porkbun's proxy rather than your home address.
  6. Pay. Card, PayPal, or crypto. Expect a few cents of ICANN fee on top of the sticker price.
  7. Verify the email ICANN sends you. Do this now, not later.
  8. Check the toggles. In Domain Management, confirm auto-renew is on and domain lock is on. Both are on by default; confirm anyway.
The 15-day clock

Within minutes of registering, ICANN sends a verification email to the address you registered with. If you do not click that link within 15 days, the domain is suspended — it stops resolving, and your site goes dark with no obvious cause.

It is the single most common way a new domain quietly breaks. Check your spam folder if it has not arrived within the hour.

Picking the name

You need exactly one domain. TREK lives on a subdomain — trek.lunabun.app — so a single registration covers this project and anything you build later.

Avoid free TLDs like .tk: they get revoked without notice and are widely blocklisted, which would silently break TREK's notification emails.

About .app and .dev

.app and .dev are on the HSTS preload list at the TLD level, so browsers refuse plain HTTP on them permanently. This deployment is unaffected — Caddy issues a real certificate in stage 09 and every request is HTTPS from the start regardless. If anything the TLD is a small bonus: protocol-downgrade attacks are impossible by construction.

Certificate issuance is unaffected too, despite what you will find in forum threads. HSTS preload is a browser mechanism. Let's Encrypt's validators are not browsers, do not consult the preload list, and Caddy answers the ACME challenge on port 80 before any redirect happens.

The one real consequence is a debugging one, in the troubleshooting table below: you cannot open http:// in a browser to inspect a proxy error. Use curl and the container logs instead.

This guide assumes trek.lunabun.app. A subdomain keeps the apex free for a website later, and it makes the Caddy config and the certificate scope obvious. If you would rather use the bare domain, substitute it everywhere and use @ as the record hostname in stage 06.

05

Close the network down

Go to Networking → Firewalls → Create Firewall. Name it trek-fw.

Delete the default inbound rules and build exactly this set:

TypeProtocolPortSources
SSHTCP22Your home IP if it is static; otherwise All IPv4, All IPv6
HTTPTCP80All IPv4, All IPv6
HTTPSTCP443All IPv4, All IPv6
CustomUDP443All IPv4, All IPv6

Leave the outbound rules at their permissive default — TREK makes outbound calls for weather, maps, place search and Let's Encrypt. Under Apply to Droplets, select trek-prod, then create.

Port 80 has to stay open even though everything redirects to HTTPS: that is how Let's Encrypt validates your domain. UDP 443 is HTTP/3, which Caddy serves and which noticeably helps on mobile connections.

Why the cloud firewall and not UFW

Docker writes its own iptables rules that sit in front of UFW, so a published container port is reachable even when UFW claims to be blocking it. It is one of the most common self-hosting mistakes.

The DigitalOcean firewall runs on the hypervisor, outside your droplet entirely, so Docker cannot punch through it. That is your real perimeter. Note that port 3000 is absent from the table above — and the compose file never publishes it to the host, so it is closed twice over.

07

Harden the server

First connection. Accept the host fingerprint when prompted.

Your Mac · Terminal
ssh -i ~/.ssh/trek_do root@YOUR_DROPLET_IP

Patch, and set a timezone

Droplet · root
apt update && apt upgrade -y
timedatectl set-timezone UTC

Create a non-root user

You will run TREK as this user, not as root. It inherits your SSH key.

Droplet · root
adduser --gecos "" --disabled-password trek
usermod -aG sudo trek
rsync --archive --chown=trek:trek ~/.ssh /home/trek/

--disabled-password means exactly that: the account has no password, so nobody can log in as trek by typing one. Your SSH key is the way in. But sudo asks for your own password before escalating, and an account with none can never satisfy it — so set one now:

Droplet · root
passwd trek

Choose something strong and put it in your password manager. You will never type it to log in — that is what the key is for — only when sudo asks. Two different secrets guarding two different things: the key gets you onto the box, the password gets you root.

The passwordless alternative

Some people prefer sudo that never prompts:

echo 'trek ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/trek && chmod 440 /etc/sudoers.d/trek

It is convenient, and defensible here given SSH is key-only and root login is off. But it collapses two barriers into one: anything that gets a shell as trek — a compromised key, a bad dependency in something you run — is instantly root. The password is thirty seconds of typing a week. Prefer it.

Turn off root login and passwords over SSH

Write a drop-in rather than editing sshd_config directly — DigitalOcean images ship cloud-init files in sshd_config.d/ that would override your edits.

Droplet · root
cat > /etc/ssh/sshd_config.d/99-trek.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF

sshd -t && systemctl restart ssh
Test before you close this window

Keep the current root session open. In a second terminal, prove the new user works:

Your Mac · Terminalnew window
ssh -i ~/.ssh/trek_do trek@YOUR_DROPLET_IP

Only once that lands at a shell prompt should you close the root session. If it fails, you still have the root window to fix it — otherwise your only way back in is the browser-based Droplet Console recovery.

Add swap

On a 2 GB droplet this step is load-bearing, not optional. The client bundle peaks at about 1.1 GB and the headroom above that is thin — swap is what turns a tight build into a safe one. It costs nothing while idle.

Droplet · root
fallocate -l 4G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# Prefer RAM; use swap only under real pressure.
echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
sysctl -p /etc/sysctl.d/99-swappiness.conf

free -h

Automatic security updates

Droplet · root
apt install -y unattended-upgrades
cat > /etc/apt/apt.conf.d/20auto-upgrades <<'EOF'
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
EOF

Deploy from your fork

I added three files to your repo for this — a production compose file, a Caddy config, and an env template. They are committed to your fork, so the droplet gets them with the clone.

Clone it

Droplet · trek user
git clone https://github.com/OHHHHAYO/TREK.git /opt/trek
cd /opt/trek
mkdir -p data uploads

Configure

Generate the encryption key first and keep the output visible — you need to paste it in a moment.

Droplet · trek user
cp .env.example .env
chmod 600 .env
openssl rand -hex 32
nano .env

Fill in these five. Everything else has a working default.

VariableValue
TREK_DOMAINtrek.lunabun.app — Caddy requests a certificate for exactly this name
APP_URLhttps://trek.lunabun.app — used for CORS and links in notification emails
ENCRYPTION_KEYThe 64-character hex string you just generated

Leave ADMIN_EMAIL and ADMIN_PASSWORD blank; TREK will print a generated admin password to the log on first boot, which avoids ever writing one to disk.

Back up the encryption key now

ENCRYPTION_KEY encrypts every secret TREK stores — API keys, MFA seeds, SMTP credentials, OIDC secrets — with AES-256-GCM. Lose it and no backup can recover them.

Put it in your password manager before you continue. Not in the repo, not in a note on the droplet: a backup and its key sitting on the same disk protect you from nothing.

Build and launch

This compiles the shared library, the React client and the NestJS server from your fork's source, then assembles the runtime image. Expect 10–25 minutes on this droplet the first time. Later builds reuse cached layers and are far quicker.

Droplet · trek user
cd /opt/trek
docker compose -f docker-compose.prod.yml up -d --build

Watch it come up:

Droplet · trek user
docker compose -f docker-compose.prod.yml logs -f

Caddy logs a certificate obtained for your domain within a few seconds of starting, provided stage 06 resolved correctly. Press Ctrl-C to stop following — the containers keep running.

10

First login, then lock the app down

Retrieve the generated admin credentials from the boot log:

Droplet · trek user
docker compose -f docker-compose.prod.yml logs trek | grep -iA4 'admin'

Open https://trek.lunabun.app and sign in. Then, in order:

  1. Change the admin password immediately. TREK enforces 8+ characters with mixed case, a digit and a symbol, hashed with bcrypt.
  2. Enable two-factor auth on your account under user settings. You must have it on yourself before you can require it of anyone else.
  3. Turn off open registration in Admin → Users unless you genuinely want strangers signing up. Invite links are the better way to add people.
  4. Configure automatic backups in the admin panel — schedule and retention. This is TREK's own internal backup, separate from stage 11.
  5. Install it as an app: on iOS, Share → Add to Home Screen; on Android, Menu → Install app. This works now only because you have real HTTPS.
Optional: Unsplash key

Trip-cover and place-image search uses Unsplash. Datacenter IP ranges — including DigitalOcean's — are frequently blocked from its unauthenticated endpoint, so image search may silently return nothing from a VPS.

A free key from unsplash.com/developers fixes it. Put it in UNSPLASH_ACCESS_KEY in .env and re-run the up -d command.

Nightly archive on the droplet

SQLite runs in WAL mode, so copying travel.db mid-write can capture a torn state. The script stops the container for the few seconds the archive takes — the simple guarantee of consistency — and restarts it even if the archive fails.

Droplet · trek user
crontab -e

# add this line — 03:15 nightly
15 3 * * * /opt/trek/deploy/backup.sh >> /opt/trek/backups/backup.log 2>&1

Run it once by hand first, so you find out now rather than during an incident:

Droplet · trek user
/opt/trek/deploy/backup.sh

Pull a copy to your Mac

Your Mac · Terminal
mkdir -p ~/trek-backups
rsync -avz -e "ssh -i ~/.ssh/trek_do" \
  trek@YOUR_DROPLET_IP:/opt/trek/backups/ ~/trek-backups/
A backup you have never restored is a hypothesis

Once, on purpose: copy an archive somewhere scratch, extract it, and confirm data/travel.db and your uploads/ files are really in there. Restoring is the reverse of the script — stop the stack, replace data/ and uploads/, start it again.

Updating and rebuilding

Three different things get called "updating", and they need different commands. Find your row first.

What changedWhere you startGo to
Your own code or deploy configPush from your MacThe standard update below
Upstream released a new TREKMerge upstream into your fork firstTracking upstream
Only a value in .envEdit on the droplet — nothing to pulldocker compose -f docker-compose.prod.yml up -d, no rebuild
Never press the admin panel's “How to Update” button

The banner reading TREK vX is available is upstream's notifier, and its button shows upstream's instructions: docker compose pull, or a bare docker run. Those are written for people running the published image with no reverse proxy.

Run them here and you replace your fork's build with upstream's and drop the container off Caddy's network — the site returns 502 while the container looks perfectly healthy. The banner is a notification, not a button.

The standard update

Four steps, in this order. Steps 1 and 4 are the ones people skip and later wish they had not.

1. Back up. Cheap, and it doubles as a check that your backup script still works.

Droplet · trek user
cd /opt/trek
./deploy/backup.sh

2. Pull and rebuild. The export derives the version from package.json so it can never go stale; a shell variable overrides whatever .env says.

Droplet · trek user
cd /opt/trek
git pull

export APP_VERSION="$(grep -m1 '"version"' package.json | cut -d'"' -f4)+fork"
echo "building $APP_VERSION"

docker compose -f docker-compose.prod.yml up -d --build
docker image prune -f

3. Reconcile .env — see the warning below. Skip only if you know no new variables were added.

4. Verify. Both containers healthy, and the app answering over TLS:

Droplet · trek user
docker compose -f docker-compose.prod.yml ps
curl -fsS https://trek.lunabun.app/api/health

If either looks wrong, read the logs before touching anything else:

Droplet · trek user
docker compose -f docker-compose.prod.yml logs --tail 40 trek
git pull never updates your .env

.env is gitignored — it holds your live secrets and git will not touch it, in either direction. So when a new setting is added, it arrives in .env.example and your real .env silently stays as it was. The app then runs on a default you did not choose.

After any pull that touched the template, diff the two and copy across what is missing:

Droplet · trek user
cd /opt/trek
diff <(grep -o '^[A-Z_]*=' .env.example | sort) \
     <(grep -o '^[A-Z_]*=' .env | sort)

Lines marked < exist in the template but not in your file. Add them with nano .env, then re-run step 2's up -d.

Caddy's certificatesPreservedNamed volume caddy_data; survives down and up
Application code, node_modulesRebuiltBaked into the image from your fork's source
Database schemaMigrated forwardRuns automatically at boot, and does not roll back — hence step 1

Because only the image is replaced, an update is normally quick: unchanged layers come from cache, so a config-only change rebuilds in a minute or two rather than the 10–25 of the first build.

Tracking upstream

Your fork does not receive upstream commits on its own. Wire up the remote once, on your Mac:

Your Mac · Terminal
cd ~/Desktop/TREK
git remote add upstream https://github.com/liketrek/TREK.git
git fetch upstream

Then, whenever the banner reports a genuinely newer release:

Your Mac · Terminal
git fetch upstream
git merge upstream/main        # resolve conflicts if you have edited the same files
git push origin main

Then run the standard update on the droplet. Because step 2 reads the version out of package.json, merging an upstream release automatically bumps what the admin panel reports and clears the banner — there is no version number to maintain by hand.

Why APP_VERSION has to be real semver

It drives two things: the update banner, which compares it against upstream's latest release, and the plugin compatibility gate. A value like fork or dev fails semver.valid(), and an unparseable host version does not merely break the banner — it silently switches the plugin gate off, letting a plugin built for a different TREK major load anyway.

3.4.1+fork is the right shape. Everything after + is build metadata, which is legal semver and still compares as the release underneath it — so you get an accurate banner, a working gate, and a string that identifies this as your build.

Read the release notes before a major version

Migrations run automatically at boot and are forward-only. Before any upgrade that crosses a major version, run ./deploy/backup.sh and read the upstream releases page for breaking changes.

If an update goes wrong

Roll the code back and rebuild. Your data is untouched by this — only the image changes.

Droplet · trek user
cd /opt/trek
git log --oneline -5                    # find the commit that worked
git checkout <commit-sha>
docker compose -f docker-compose.prod.yml up -d --build

If the database itself was migrated by the bad version, code alone will not fix it — restore the archive from step 1:

Droplet · trek user
cd /opt/trek
docker compose -f docker-compose.prod.yml down
tar -xzf /opt/trek/backups/trek-YYYYMMDD-HHMMSS.tar.gz -C /opt/trek
docker compose -f docker-compose.prod.yml up -d

Return to the tip of your branch afterwards with git checkout main.

If builds get tedious

Building on the droplet is self-contained, which is why it is the default here. If you end up deploying often, move the build to GitHub Actions in your fork, push the image to GHCR, and have the droplet only pull it. Deploys drop to seconds, and the droplet no longer needs build headroom. Worth doing once you are shipping changes regularly — not before.

Running more apps on this droplet

One domain can absolutely host several apps — but give each one its own subdomain, not a path. lunabun.app/trek does not work, and the reason is in TREK's source rather than in your proxy config.

Why not /trek

LayerWhat it assumesEffect at /trek
Vite buildNo base configuredAssets are requested from /assets/… — 404 on every script and stylesheet
React RouterBrowserRouter with no basename/trek/trips matches no route; navigation lands nowhere
API clientbaseURL: '/api', plus ~958 hardcoded /api/… call sitesEvery request goes to the wrong origin path
WebSocket`${protocol}://${location.host}/ws` — built from the host, prefix ignoredReal-time sync never connects
Server routes/api, /ws, /uploads, /oauth, /.well-known mounted at rootWould each need a prefix-aware rewrite
Session cookiepath: '/'Scoped to the whole origin regardless

There is no BASE_PATH setting and no Nest global prefix — sub-path hosting is simply not a supported mode. Proxy rewrites cannot fix it, because the broken URLs are baked into the JavaScript the browser has already downloaded. Making it work means patching the Vite config, the router, the WebSocket builder and every call site — a fork that would conflict on every upstream merge, forever.

Subdomains are the better design anyway

This is not a consolation prize. Browsers scope cookies and localStorage by origin, so several apps sharing lunabun.app share one cookie jar — an XSS flaw in any one of them can read TREK's session cookie. Separate subdomains are separate origins, and the browser enforces the boundary for you.

You also get a clean PWA scope and an independent certificate per app.

The pattern

One droplet, one Caddy, many apps — each on its own hostname and its own internal port, none of them published to the host.

1. DNS. In Networking → Domains, add one A record per app, each pointing at the same droplet:

TypeHostnameWill direct to
AtrekDroplet IPv4
AblogDroplet IPv4
AwhateverDroplet IPv4

A wildcard * record works too and saves a step per app, at the cost of every typo'd subdomain resolving to your droplet. Explicit records are easier to reason about until you are adding apps often.

2. A shared Docker network, so Caddy can reach containers that live in other compose projects:

Droplet · trek user
docker network create web

Then add it to each service in docker-compose.prod.yml, and declare it as external at the bottom of the file:

Droplet · trek userdocker-compose.prod.yml
services:
  trek:
    networks: [web]
    # ... rest unchanged
  caddy:
    networks: [web]

networks:
  web:
    external: true

3. One Caddy site block per app. Caddy fetches a separate certificate for each hostname automatically, and refuses hostnames it has no block for.

Droplet · trek userdeploy/Caddyfile
{$TREK_DOMAIN} {
	encode zstd gzip
	request_body {
		max_size 500MB
	}
	reverse_proxy trek:3000 {
		flush_interval -1
	}
}

blog.lunabun.app {
	encode zstd gzip
	reverse_proxy blog:8080
}

Reload Caddy without dropping connections:

Droplet · trek user
docker compose -f docker-compose.prod.yml exec caddy \
  caddy reload --config /etc/caddy/Caddyfile
Watch the ceiling

The 4 GB droplet comfortably runs TREK plus a couple of small services. It will not run TREK plus a second database-backed app plus an image processor — and because TREK holds its database on local disk, the fix when you outgrow the box is a bigger box, not a second one.

Keep an eye on free -h and df -h, and set a DigitalOcean alert policy on memory while you are adding things.
